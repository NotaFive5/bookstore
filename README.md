# Synergy Bookstore

Веб-версия книжного магазина с пользовательским и административным интерфейсами. Учебный проект к кейс-задаче №4 производственной (технологической) практики.
Факультет информационных технологий, направление 09.03.02 «Информационные системы и технологии», профиль «Веб-разработка».
АНО ВО «Московский университет «Синергия», 2026 г.

## Запуск

Открыть `index.html` в браузере. Серверная часть не требуется.

## Стек технологий

- **React 18** через CDN — пользовательский интерфейс, hooks, Context API
- **Babel Standalone** — JSX-транспиляция в браузере
- **Tailwind CSS** через CDN — стилизация
- **localStorage** — клиентское хранилище данных
- **Canvas API** — сжатие обложек книг до 600 px по ширине

## Реализованный функционал

В соответствии с требованиями кейс-задачи №4:

1. **Web-страница** — адаптивный SPA-интерфейс, корректно отображается на десктопе, планшете и мобильном.
2. **Два интерфейса** — `user` и `admin`. Доступ к админ-разделам ограничен ролью.
3. **База данных книг** — встроенный каталог из 6 любимых книг (классика, IT, антиутопия, научпоп). Расширяется администратором.
4. **Просмотр книг пользователем** — карточки в каталоге, детальный просмотр в модальном окне с обложкой, описанием, ценой, рейтингом и отзывами.
5. **Сортировка** — по названию, автору, году (новые/старые), цене (↑/↓), пользовательскому рейтингу.
6. **Фильтры и поиск** — по категории, автору, году, текстовый поиск по названию и автору.
7. **Покупка книги** — фиксация транзакции в личной библиотеке с датой и ценой.
8. **Аренда книги** — на 2 недели (15% от цены), 1 месяц (25%), 3 месяца (55%). Автоматический расчёт даты возврата.
9. **Возврат арендованной книги** — пользователь может вернуть досрочно.
10. **Админ-функции** — CRUD книг (создание, редактирование, удаление), управление ценой, статусом (в каталоге / архив), доступностью.
11. **Загрузка обложек** — администратор загружает изображение, оно сжимается через Canvas API и сохраняется в base64.
12. **Автоматические напоминания об окончании аренды** — при загрузке приложения проверяются активные аренды, генерируются уведомления за 3 дня до окончания и при просрочке. Уведомления видны пользователю в отдельной вкладке.
13. **Контроль аренд для администратора** — отдельный экран со списком всех аренд, выделение скоро завершающихся и просроченных.

Дополнительный функционал:

- **Отзывы и рейтинги** — пользователь оставляет 5-звёздочный отзыв с текстом, средний рейтинг отображается в карточке книги.
- **Дашборд администратора** — суммарная выручка, число покупок, активных аренд, ТОП-5 книг по продажам/арендам.
- **Личная библиотека пользователя** — статистика (куплено / в аренде / всего потрачено), списки покупок и аренд с цветовой индикацией (просрочка / скоро возврат / активна).

## Подробный анализ выполненной задачи

1. **Архитектура**. Single-page application с разделением на роли (user / admin) и независимыми view-компонентами для каждого экрана. Маршрутизация выполнена через локальное состояние tab, что для учебного приложения проще полноценного router-а.

2. **Модель аренды**. Аренда моделируется отдельной транзакцией с явными датами начала и окончания. Это упрощает построение отчётов, фильтрацию по статусу и автоматическую генерацию уведомлений по времени.

3. **Стоимость аренды**. Реализована через прогрессивный множитель: 15% / 25% / 55% от цены книги для 2 недель / 1 месяца / 3 месяцев. Это даёт стимул брать на больший срок.

4. **Автоматические уведомления**. При каждой загрузке приложения сканируются активные аренды, и для тех, до окончания которых осталось <3 дня (или которые уже просрочены), создаются записи в `notifications` с привязкой к пользователю. В боевой версии эта же логика выносится на серверный cron.

5. **Изображения**. Обложки загружаются администратором и сжимаются на клиенте перед сохранением в localStorage. Для боевой системы потребуется объектное хранилище (S3/MinIO).

6. **Роль-ориентированный доступ**. Админ-вкладки скрыты у пользователей и недоступны при попытке перейти напрямую, так как рендер происходит с проверкой `currentUser?.role === 'admin'`. На клиенте этого недостаточно — в боевой системе нужна серверная проверка JWT-claim.

7. **Отзывы**. Хранятся отдельной коллекцией с уникальностью пары (book, user) — повторный отзыв перезаписывает старый. Средний рейтинг вычисляется на лету.

## Рекомендации по устранению выявленных недостатков

- Интегрировать настоящий эквайринг (ЮKassa / Stripe) для реальных платежей вместо имитации.
- Перенести логику ролей и проверки прав на сервер, использовать JWT с ролью в claim и middleware на маршрутах.
- Использовать объектное хранилище для обложек, выдавать pre-signed URL.
- Реализовать DRM или watermarking для электронных копий книг.
- Внедрить рекомендательную систему на основе истории покупок (коллаборативная фильтрация).
- Перевести cron-логику уведомлений на сервер (node-cron + воркер) с отправкой реальных email через nodemailer.
- Добавить логирование действий администратора (audit log).
- Реализовать end-to-end тесты критичных сценариев (Playwright).
- Реализовать резервное копирование данных.
